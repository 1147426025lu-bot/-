二、复现步骤（在支撑材料解压后的根目录按序执行）
  1) 环境：Python 3.14.0；numpy 2.3.5、scipy 1.18.1、pandas 2.3.3、
     matplotlib 3.10.8、seaborn 0.13.2、networkx 3.7、openpyxl 3.1.5。
     中文 Windows 的控制台默认 GBK，需设 PYTHONIOENCODING=utf-8 再运行，
     否则脚本的中文输出与文件名会报编码错。随机种子只走 PYTHONHASHSEED。
  2) 求解（按序执行，后一步读前一步落盘的方案记录）：
       python code/q1.py
       python code/q2.py --engine v2 --seeds 5 --iters 3500 --k-targets 20,22,25,30
       python code/q2_exact.py
       python code/q3.py
       python code/q4.py
     实测单次耗时：q2 约 1712.2 s、q3 约 172.7 s（其余在分钟级）。
     注：q1.py 的 ILP_TIME_LIMIT 为 300 s/阶段（早期版本为 60 s）。60 s 下
     集合划分 ILP 的结论会随机器忙闲翻转（S001 时而是"一致"、时而是"未复核"），
     那本身不可复现；抬到 300 s 后 15/15 全部一致，且超时仍如实记为"未复核"。
     问题二的种子 20260923、K 档位 20/22/25/30（由 --k-targets 给出）；落盘方案
     要过"问题二同指标候选解之间的中继门禁"才交给第三问，见第三节第 4 条。
     问题三的逐时刻审计步长 1.0 s、搜索步长 2.0 s。
     任一落盘记录被改动、或其源码哈希失效时，加载器会拒绝读入并报错，
     不会静默使用过期方案——遇到报错请从 q1 起重跑整链。
  3) 复核：code/verify.py（应退出码 0，11 项全过）；
          code/tests_regression.py（应 32 项全过、0 跳过）。
  4) 数字与图表：code/make_seed_stats.py、code/make_q3_sens.py、code/make_q4_sens.py、
     code/make_data_table.py、code/make_delivery_table.py —— 这五个是**只读派生**
     脚本：只调用求解器的既有函数、一律 save=False，不写任何方案记录，也不在
     求解器哈希清单内，故可单独重跑而不作废已落盘的方案；随后 code/paper_metrics.py
     → code/fill_results.py → code/figures.py → code/figures_adv.py →
     code/make_roadmap.py、code/make_q2_algorithm.py → code/render_drawio.py
     （每个 .drawio 各传一次路径）→
     latexmk -g -xelatex -interaction=nonstopmode main.tex。
     论文正文的数字不由人工誊写：全部 \mtXXX 宏来自 results/paper_metrics.json。
     排版门禁四条（在 main.log 上数）：Overfull \hbox、Overfull \vbox、
     Reference .* undefined、Citation .* undefined 各为 0，且摘要恰一页。
     这四条连同"摘要恰一页"已并成一次调用：code/check_layout_gates.py，
     退出码 0 即全过；缺 pdftotext 时它如实报"未判定"并按失败退出。
     Underfull 不计入门禁（干净基线本就有数十条）。
  5) 打包：python build_submission.py --check 先预检，再不带参数执行。包内不放
     main.pdf（论文成品单列在 论文/ 下），故预检要求先由第 4 步编出 main.pdf；
     清单缺项时预检会逐条列出并中止，不会产出一个"看起来完整"的包。

三、交付一致性的四条硬规矩（改动前先读）
  1) 数据清单只有一个来源：code/solution_io.py 的 input_hashes()。方案记录里的
     输入身份覆盖 数据/ 下全部 17 个文件，打包器也打这 17 个。只打其中"代码
     真正读得到"的 6 个，评委解压后每条方案都会被判"输入数据不一致"而被加载器
     拒绝——包看着完整，却一条都跑不通。
  2) 源码哈希按**字节**计算，于是换行符也算差异。本工程源码的换行并不统一
     （脚本以文本模式写出的文件是 CRLF，编辑器写出的文件是 LF），.gitattributes
     已逐个锁定：code/core.py、code/q2.py 为 CRLF；code/q3.py、
     code/solution_io.py、code/q2_v2.py、code/q3_v2.py、code/q3_chain.py 为 LF。
     改动这七个文件
     会让 results/q2_solution.json、results/q3_solution.json 当场失效——那不是
     "代码算错了"，而是记录需要重出，唯一正路是按第二节第 2 步重跑整链。
     results/_q2_hash_refresh.txt 是 2026-09-24 的一次**历史**记账修补留痕，
     已由 2026-09-25 的整链重解取代，不再描述当前状态；保留它只为留下改过什么。
  3) LiSu.ttf 是第三方商业字体，授权不允许再分发：本包不含它。gmcmthesis.cls
     已改为三级回退（工程内 LiSu.ttf → 系统隶书 LiSu/STLiti → 楷体），实测在
     没有该文件的目录下 xelatex 仍以退出码 0 编出全文。
  4) 问题二 → 问题三之间有一道**中继门禁**（code/q2_v2.py 的 relay_feasible_order）。
     问题二的目标函数对"同一架次内服务区的先后次序"不敏感，故存在这样一批候选：
     把同一架次内的两个服务区互换，五项报告指标逐位不变。**措辞须注意**：问题二的
     全局最优性未获证明（两层精确解只标定了小规模算例），这批候选只是实际枚举并
     完整评价后筛出来的同指标解；论文 7.5 节、摘要与附录 A 一律称"同指标候选解"，
     不称"最优解的等价类"。门禁在保持这五项指标逐位不变的前提下，按第三问的字典序键
     （无绑定区间数、缺口秒数、累计推迟、联合完工、中继能耗）在这批候选之间择序。
     本算例 25 个候选中有 3 个指标逐位不变，选中「U06 第 6 位与第 8 位互换」，
     第三问中断由 0.6688% 降为 0。
  5) results/q3_relay_trips.csv 的**一行 = 一次悬停站服务**（表头「中继架次编号」
     R01..Rn 是这张表的主键，失效区间、通信保障分段、Excel 回填都按它连接）。
     自阶段 13 起，一次**出动**（一次从 O01 出发、返回 O01 的完整行程）可以依次
     服务多个悬停站，于是表里另有三列：「出动编号」D01..Dm、「架次内序」（该站是
     本次出动的第几站）、「本访问能耗kWh」（本次进场航段 + 本站悬停的能耗份额，
     该次出动的**末次**访问另含末端返航，故同一出动的份额之和恒等于其架次能耗）。
     注意口径：「开始时刻s」「返回O01时刻s」「架次能耗kWh」是**出动级**字段，在
     同一次出动的每一行上取同值——凡按占用、能耗或工作量计的场合（资源峰值并发、
     能耗汇总、占用甘特图）都必须先按「出动编号」去重，逐行相加会把同一次出动
     重复计入。code/verify.py 与 code/figures_adv.py 都各自做了这一步，并在
     verify.py 里以「出动内能耗份额求和偏差」一栏独立复核。
  6) code/q3_legacy.py 是阶段 13 之前的中继排班器（旧 q3.schedule_relays）的**逐字
     副本**，只服务于两处对拍：code/tests_regression.py 的 T23 与 _probe/ 下的
     阶段 13 探针，用它在同一批 job 上证明「不连飞档与旧实现逐位一致」。它**不在
     求解路径上**（q3.py 与 q3_chain.py 都不 import 它，论文里的任何数字都不是它
     算的），因此也不在 solution_io.Q3_SOLVER_FILES 的哈希清单里。

    用来说明"换一组种子结果不会面目全非"（K<=30 档 5 个种子中 4 个落到四项指标逐位
    相同的解），**它不构成最优性证明**——交付解仍是固定种子 20260923 的那一个，
    其质量由两层小规模精确解（code/q2_exact.py）标定；
  · code/verify.py 与求解器共享公共物理模块 code/core.py，它排除的是"求解程序
    内部状态与结果表之间的串号、漏检与自我印证"，不能排除公共物理口径本身出错；
  · 问题四"全部分区中的最小需求"由 code/q4.py 枚举得出，verify.py 只核对它与
    推荐需求、库存三者自洽、不重跑枚举；该列的真值由 tests_regression.py 的
    T-Q4m 以一次独立枚举逐类核对；
  · 问题三的中继方案由**联合调度**路径给出。另一条"运输重排 ↔ 中继归属"固定点
    迭代路径（code/q3_v2.py）在本算例 2 轮即收敛（累计释放 0 s → 709 s 后不再增长），
    其末端解与主路径**逐项相同**（缺口 0 s、加权迟到 0、累计推迟 709 s、联合完工
    6641.7 s、中继能耗 3.677 kWh），故按"不更优则不替换"的规则**未被采用**。
    须一并记录的是它的收敛性并不稳固：在问题二采用同指标候选筛选门禁**之前**的派工顺序上，
    同一条路径 12 轮内未收敛、累计释放单调增至 33388 s、末端仍留 1694 s 缺口，
    在字典序每一层上都劣于当时的主路径。论文 7.5 节已如实记录这两组结果，
    既不称其"有效"、也不静默丢弃；
  · 问题四的两类分区在给定库存下均不可行，本文只给出补配清单，**未给出**任何
    可行分区方案。不可行的成因是**联合约束**而非任何单类短缺：K=2 与 K=3 下八类
    资源在全部分区上的最小缺口**全部为 0**。K=3 时中继无人机的下界 K-1=2 恰好
    等于库存 2、余量为 0，是最贴近临界的一处，但该下界本身不构成结构性短缺。
    （此处早期版本曾记为"K=3 中继缺 1 架是结构性短缺"，已由本轮完全枚举证伪。）
